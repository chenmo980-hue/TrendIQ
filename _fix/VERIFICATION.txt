更新时间：2026-09-16 23:38
工作区：E:\\WorkSpaces\\TrendIQ

## 一、问题真因

用户贴出 400 错误原文：
  诊断：请求未完成
  HTTP 400 Bad Request · Requested model DeepSeek-V4-Pro not supported
  400：中继拒绝了这次请求...

磁盘里保存的模型 DeepSeek-V4-Pro 在该中继上实际无通道。用 Node 直连同一个中继
POST /chat/completions 拿到的正是这个 400。

## 二、Node 实测中继 9 个模型

| 模型               | HTTP | 耗时   | 结果 |
|--------------------|------|--------|------|
| auto               | 200  | 10.31s | OK   |
| step-3.7-flash     | 200  | 2.32s  | OK   |
| DeepSeek-V4-Flash  | 200  | 7.14s  | OK   |
| glm-4.5-air        | 200  | 2.02s  | OK   |
| DeepSeek-V4-Pro    | 400  | 2.03s  | not supported |
| DeepSeek-V4.1-Flash| 404  | 0.39s  | fail |
| deepseek-chat      | 503  | 0.34s  | fail |
| gpt-4o-mini        | 503  | 0.30s  | fail |
| glm-5.3            | 0    | 45s    | TIMEOUT 死通道 |

关键发现：中继的 /models 目录里列出了 DeepSeek-V4-Pro，但 /chat 端实际并不接。
因此 Models.Contains(_savedModel) == true 这种回退救不了，必须真正发一次探针。

## 三、本轮代码改动

新增 ProbeModelAsync(model)：对单个模型发一个 max_tokens=1 的极小请求，能用返回 true。

FetchModelsAsync 拉完列表后：
  - 若 _savedModel 在列表里 -> 调 ProbeModelAsync
    - 成功 -> 保留 SelectedModel = _savedModel
    - 失败 -> 清空 _savedModel，SelectedModel = Models.FirstOrDefault()，
             状态栏显示 "已保存的 XXX 在该中继上实际不可用，已自动切换到 YYY"
  - _savedModel 不在列表里 -> 保持原回退逻辑

## 五、用户操作

1. 重新构建并发布后，到桌面双击 dist\\ApiTester.exe。
2. 首次启动会自动拉模型 + 自动测活保存的那个模型。
3. 状态栏出现 "已保存的 DeepSeek-V4-Pro 在该中继上实际不可用，已自动切换到 auto"
   （或实际回退到的其他可用模型），下拉框自动选中 auto。
4. 点发送消息即用 auto 调 /chat/completions，按 Node 实测会 200 成功。

无需手动改任何配置，无需重新选模型。

## 六、备选手工绕开

手动把磁盘里 %APPDATA%\\ApiTester\\settings.json 的 SelectedModel 改成上面 OK 之一
（推荐 auto 或 step-3.7-flash）。下次启动直接就是好模型，不需测活。
